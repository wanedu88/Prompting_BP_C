# Keep

## 마더 프롬프트 - 엣지 프롬프트
어떠한 참고할 만한 '원본 큰 절차' 가 있는 경우, 거기에 적용된 방법론을 다른 case에 전이시키고 싶다면 유용함
혹은 세부적인 각각의 프롬프트를 아우르는 큰 틀을 먼저 생성하고, 만들어진 큰 틀을 이용하여 세부 프롬프트를 다시 만들고 싶다면 유용함

 - 마더 프롬프트 : 엣지 프롬프트의 기초로 사용할 거대 프롬프트 (직접 작성 X, AI에게 정리 요구)
여러 문서나 구조설계 자료들을 하나의 파일로 취합하여 컨텍스트 통합
 - 엣지 프롬프트 : 마더 프롬프트를 베이스 컨텍스트로 사용하여 생성하는 개별 실행 프롬프트 (필요에 따라 일괄 혹은 하나씩 생성)

## 단어 명확성
 - 앞에서 사용한 단어를 뒤에서 같은 의미로 사용시 되도록이면 문자 그대로 같게 사용. 혹은 따옴표로 묶어 구절을 명확히 토큰화시킴
 - [P] [C] [T] 보다는 [Persona] [Context] [Task] 가 낫고, 대괄호보다는 #Persona #Context #Task (Markdown) 이 더 나음

# Problem

## 비결정적 동작
 - 프롬프트에서 간곡하게 부탁한다고 반드시 지켜지라는 법은 없음

## 필수 절차 누락
 - 지시했음에도 생성되는 텍스트에서 누락되거나 (프롬프트 생성 미비)
 - 지시했음에도 액션 과정에서 동작하지 않는 경우 발생할 수 있음

## 추상성 희석
 - 이론적인 방법론 문구나 학술적 단어들이 LLM에 의해 재해석되거나 왜곡될 수 있음
 - 다단계의 정보 정리, 프롬프트 재생성, 액션 과정에서 목표가 변형되거나 동작의 방향성이 달라질 수 있음

# Try

## 비결정적 동작 대응
 - 앞 프롬프트에서 언급하는 것보다 rule / RAG 로 매 단계 포함하는 것이 더 강력함
 - 서술형으로 지시하는 것보다 markdown / json 등으로 정규화시키는 것이 더 강력함
 - 규칙을 프롬프트에 포함하는 것보다 외부 도구가 terminal log 결과를 검증하는 것이 더 강력함

## 필수 절차 충족 검증
 - 각각의 프롬프트가 명시적으로 해당 동작을 하는지 사람이 검토하는 것이 좋음 - 프롬프트 내용 및 실행 여부

## 추상성 희석 방어
 - 방법론의 이론적 단어 하나하나를 구성하면서 따라가는 것보다 최대한 Lean한 구조로 프롬프트 경량화
